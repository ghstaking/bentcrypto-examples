# x402 Notes for BentCrypto

BentCrypto uses x402 v2 fixed-price (`exact`) payments. Token Risk currently offers USDC settlement on both Solana mainnet and Base mainnet; Token Security is Solana-only.

## Payment flow

1. Client sends a valid HTTP GET request without `Payment-Signature`.
2. BentCrypto validates the requested chain and token-address shape.
3. Invalid input returns a free HTTP `400` with no payment challenge.
4. Valid paid input returns HTTP `402` and a `Payment-Required` header.
5. The buyer validates the offered requirements against its wallet and local spend policy.
6. The buyer signs locally and retries the exact same request with `Payment-Signature`.
7. BentCrypto verifies/settles payment and returns the resource response.
8. Settlement metadata is returned in the `Payment-Response` header.

## Analysis chain vs. payment network

These are separate concepts:

- **analysis chain** is selected by the `chain` query parameter and tells BentCrypto which blockchain to inspect;
- **payment network** is selected from the `accepts` array inside the runtime x402 challenge.

For Token Risk, an agent can request Base analysis and still pay with an offered Solana USDC requirement, or request Solana analysis and pay with an offered Base USDC requirement. The two networks do not need to match.

## Why the example clients preflight

The JavaScript and Python examples first perform an unpaid request and inspect the challenge. They refuse to sign unless the selected requirement matches the expected production network, asset, amount, and BentCrypto receiver.

This is an additional safety layer for examples that use real mainnet USDC. The runtime challenge remains authoritative.

## Buyer examples

Solana JavaScript:

```bash
npm run token-risk
```

Base JavaScript challenge-only:

```bash
npm run token-risk:base:challenge
```

Base JavaScript paid request:

```bash
npm run token-risk:base
```

Base Python:

```powershell
python .\python\token_risk_base.py
```
